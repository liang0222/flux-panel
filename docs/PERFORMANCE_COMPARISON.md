## 4. 归因拆解：2.45 GiB 到底是谁的功劳

这是本文档最需要诚实的一节。

### 4.1 事实

优化前 agent 已连续运行 18 小时 04 分，RSS 2.5 GiB。
优化后 agent 重启，RSS 100 MB。

**"重启"这个动作本身就会让 RSS 归零**，与任何代码/配置改动无关。

### 4.2 那 `GOMEMLIMIT` 起什么作用？

`GOMEMLIMIT` **不负责"降下来"，它负责"不涨回去"**。

- 没有它：Go 堆会按 `GOGC=100` 策略一路推高，达到某个水位后**不主动归还**，
  在 `THP=always` 下尤其明显（`AnonHugePages` 曾占 RSS 的 92.7%）。
- 有它：当堆接近 1200 MiB 时，runtime 主动降低 GC 阈值，更积极回收并 `madvise` 归还。

**证据**：优化后 `HeapReleased` 从 2.8 MB 增长到 18.3 MB，说明归还机制在工作。
优化前无法观察此指标（pprof 未开），但 `VmHWM ≈ VmRSS`（差 37 MiB）说明**峰值内存从未归还**。

### 4.3 结论

| 项目 | 可信度 | 说明 |
|---|---|---|
| "agent 现在只占 100 MB" | ✅ 实测 | 但**主要是重启的效果** |
| "GOMEMLIMIT 防止重新爬到 2.5 GiB" | ⏳ **待验证** | **需 24~72 小时数据**，当前只有 24 分钟 |
| "Java 节省 164 MiB 堆" | ✅ 结构性 | `-Xms` 从 256m 降到 64m，**与重启无关，长期有效** |

**因此，唯一可以立刻写进结论的长期收益是：Java 堆 committed 从 256 MiB 降到 92 MiB。**

### 5.2 进程内存

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| `VmRSS` | 661,436 kB | 433,084 kB | −223 MiB |

**归因**：`-Xms256m → -Xms64m` 直接让堆 committed 减少 164 MiB，
THP 覆盖的大页随之减少，因此 RSS 下降 223 MiB（比堆的减少还多，因为
`AnonHugePages` 从 538 MB 降到 290 MB，多释放了 242 MB）。

### 5.3 为什么优化后 RSS 从 322 MB 涨到 433 MB

```
t+2min:  322,908 kB
t+15min: 432,120 kB
t+19min: 433,084 kB
```

这是**堆按需扩张**，属于正确行为：`-Xms64m` 让 JVM 从 64 MiB 起步，
随业务逐步 commit 到 92 MiB。**不是泄漏**（`used` 稳定在 43 MB）。

如果最终稳定在 433 MB，仍比优化前的 661 MB 低 228 MB。

### 关于 `ForwardServiceImpl` 批量查询收益的诚实结论

用生产真实数据（106 条转发、106 条端口记录）验证：

```
旧方案查询次数 = 1 + 106 + 106 + 106 = 319 次
新方案查询次数 = 1 + 3(批量)         = 4 次
```

但**实测耗时差异在本项目规模下可以忽略**：

```
旧方案（106 次逐条查询）：real 0.000s
新方案（1 次批量查询）：  real 0.000s
```

原因有两个，必须写明：

1. **`forward_port` 表没有 `forward_id` 索引**（`sqlite_master` 中该表零索引），
   无论逐条还是批量都是全表扫描，而表只有 106 行，扫描成本极低。
2. SQLite 是进程内嵌入式数据库，没有网络往返开销，N+1 的典型代价在这里并不成立。

> **因此：这项改动的价值在于代码质量与可扩展性（转发数上千时查询次数不再线性膨胀），
> 而不是当前可测的性能提升。不要把它算作内存收益。**

如果后续转发规模变大，建议补索引（**本次未做**，属数据库结构变更，需单独评估）：

```sql
CREATE INDEX IF NOT EXISTS idx_forward_port_forward ON forward_port (forward_id);
CREATE INDEX IF NOT EXISTS idx_forward_port_node ON forward_port (node_id);
```

`SIGQUIT` 拿到的堆摘要（`docker exec springboot-backend kill -3 1`，非破坏性）：

```

  region size 1024K, 15 young (15360K), 1 survivors (1024K)
 Metaspace       used 67286K, committed 67840K, reserved 229376K
  class space    used  7346K, committed  7616K, reserved 163840K
```

`/proc/<pid>/smaps_rollup` 同时刻：

```
Rss:              376712 kB
Pss:              376708 kB
Private_Dirty:    350288 kB

AnonHugePages:    272384 kB   ← 占 RSS 的 72%
```

把两者对上：

| 项目 | 数值 |
|---|---|
| 实际提交的 JVM 内存 | 堆 90 MB + Metaspace 68 MB + 其它 ≈ 160 MB |
| 进程 RSS | **368 MB** |
| 其中透明大页 | **266 MB（72%）** |
| 膨胀倍数 | 约 2.3 倍 |

THP 为 `[always]` 时，只要碰到某个 2 MB 大页里的 4 KB，整个 2 MB 都会被算进 RSS。

再看堆的绝对值：`total 92,160K` —— 比 10-30 测到的 `99,328K` **还小**。
所以 16 小时里 RSS 从 356 MB 涨到 372 MB（三个台阶：356→362→371，每级后长时间持平），
**不是堆在涨**，而是 THP 相位与 G1 区域提交的变化。堆本身没涨反降。

按小时中位数（kB）：

```
06:356104  07:358120  08:358232  09:356912  10:361936  11:362428

18:371356  19:371428  20:371532  21:371956
```

台阶式上升后持平，符合「G1 逐步提交区域 → 每个新区域触发一批大页」，

### 8.9 checkpoint 与 WAL：本轮抓到两个新事实

主库在 docker volume：`/var/lib/docker/volumes/sqlite_data/_data/`。

**事实一：定时 checkpoint 每 300 秒精确写回主库。** 340 秒 mtime 探针：

```
09:03:28 db_mtime=1793581255 db_size=3678208 wal=4132392
09:05:58 db_mtime=1793581555 db_size=3678208 wal=4132392
```

两次主库 mtime 相差 **恰好 300 秒**（1,793,581,555 − 1,793,581,255 = 300），
对应容器 `StartedAt` + initialDelay 300 s + fixedDelay 300 s 的 `@Scheduled` 相位 ——
说明 `PASSIVE` checkpoint **确实在跑且确实写回主库**，不是空转。主库大小
（3,678,208 B）在两次之间没有变化，说明只是 WAL 内容回灌，不是库在膨胀。

**事实二：WAL 已经顶到 `wal_autocheckpoint=1000` 页的上界，并稳定停在那里.**
`gost.db-wal` = **4,132,392 B**。按 WAL 帧格式反算：32 + 1,003 × 4,120 = 4,132,392，
即**恰好 1,003 帧**（跨过 1,000 页阈值）。连续 3 次 5 秒采样尺寸恒为 4,132,392 B，
而 mtime 每 5 秒推进（09:10:03 → 09:10:08 → 09:10:13）——写方在持续追加，文件却被
PASSIVE checkpoint 循环复用，不增长、不截断。

这一条**修正了第七轮 7.6 的「WAL 超过 4 MB 触发自动回写未观测到」**：
当时 WAL 高水位只有 2.2~2.3 MB，现在已到达 1,003 帧并长期停在这个尺寸。
规则上这也正是 `PASSIVE` 的固有行为——**WAL 不收缩不是缺陷**，上界由
`wal_autocheckpoint` 控制（约 4 MB）；要真正收缩只能重启容器（`onShutdown` 的
`TRUNCATE` 会做）。
