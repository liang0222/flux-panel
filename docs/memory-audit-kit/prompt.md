2. 所有前端页面及交互、视觉与布局；
3. 现有 API 路由、请求参数与返回数据结构；
4. 用户认证、登录、权限管理机制；
5. 节点管理、流量统计、端口管理；
6. 现有 IPv4 与 IPv6 功能；
7. 现有数据库结构与已有数据；
8. 现有 Docker 部署方式、数据卷、环境变量、端口映射、健康检查；
9. 现有安装脚本与升级流程；
10. 现有客户端（含移动端）兼容性；
11. 现有配置文件兼容性。

同时禁止：

16. 擅自删除任何"看起来暂时没用到"的功能；
17. 为省内存降低必要业务并发能力；
18. 为省资源造成服务响应明显变慢；
19. 破坏现有多节点部署能力；
20. 擅自更换技术栈。

若某功能实现确实有问题，可优化内部实现，但外部行为、接口、使用体验必须一致。需要改数据库结构 / API 协议 / 认证体系 / 部署方式时，**先做兼容性分析，不允许破坏性变更**。

## 2. 事实纪律（本项目最重要的一条）

**没有证据，不要编造结论。没有实际测试，不要声称优化成功。**

- 必须区分：**A** 已通过实际数据确认 / **B** 代码分析发现的高风险 / **C** 可能存在但需生产数据验证 / **D** 不影响内存但影响性能或代码质量。
- 每条结论注明：文件路径、代码位置、问题描述、原因、影响范围、风险等级、推荐方案、预期效果、验证方式。
- 无法实测的指标标 `未测试 / 未验证`。**禁止伪造内存下降比例。**
- 禁止把推测写成事实；区分"进程释放了对象"与"内存已归还操作系统"。

## 3. 语言占比不等于内存占比

仓库语言构成（例：Go 58.9% / TypeScript 19.7% / Java 19.2%）**只代表代码文件占比**。不得因为 Go 占比最高就认定 Go 是内存消耗最大的服务。必须结合实际部署结构、容器、进程与运行指标判断。

## 4. 第一阶段：只读审计（先不要改代码）

### 4.1 架构与服务拓扑
检查：项目入口、模块依赖、启动/停止流程、后台任务、定时任务、数据库连接、服务通信、缓存机制、节点通信、API 调用、外部依赖、Docker 部署关系。

必须回答：
1. 实际由哪些服务组成？
2. 每个服务是否必须独立运行？
3. 是否存在功能重复的服务？
4. 是否存在重复维护的代码？
5. 是否存在多个服务重复加载相同数据？
6. 是否存在不合理的服务依赖？
7. 是否存在不必要的常驻服务？

**必须识别的七类**：哪些在云服务器跑、哪些只用于客户端、哪些需长期驻留内存、哪些只是构建时运行、哪些可能重复运行、哪些能优化启动方式、哪些资源可能没被正确释放。

### 4.2 AI 二次开发可能引入的问题
重复实现同一功能、同一业务多版本代码、重复创建连接池、重复初始化全局对象、重复注册定时任务、重复启动后台任务、重复读配置、重复查数据库、不必要的数据复制、不合理的抽象层、过度封装导致资源浪费、无效兼容代码、已废弃但仍运行的逻辑、不再使用的依赖、重复引入的第三方库、复杂度不必要的设计模式。

**不要为了追求代码简洁而盲目删除代码。** 每项判断都必须结合实际调用关系与业务功能。

## 5. 第二阶段：Go 深度内存优化

重点 `go-gost/` 及所有 Go 服务。

### 5.1 Goroutine
是否持续增加、无限循环、阻塞 Channel、后台任务不退出、缺 context 取消、任务完成后不释放、重复创建、请求结束后仍运行。用 `runtime.NumGoroutine()` + pprof 看**增长趋势**（多日采样拟合截距，不只看单点）。

### 5.2 Heap
Map 无界增长、Slice 长期持有大数据、全局变量保留大对象、缓存无上限、大量重复对象、不必要复制、字符串拼接临时对象、大对象长期引用、不合理内存池、`sync.Pool` 误用。
分析 `HeapAlloc / HeapInuse / HeapIdle / HeapReleased / StackInuse / Sys / Alloc / TotalAlloc / NumGC / PauseTotalNs`，判断 GC 是否频繁、堆是否持续增长。

### 5.3 连接与资源释放
HTTP Body 是否关闭、TCP 是否及时释放、数据库连接是否正确使用、文件句柄是否泄漏、Socket 是否异常积累、DNS 是否重复查询、`http.Transport` 是否重复创建、连接池是否过大、超时是否合理、代理连接是否正确回收、WebSocket 是否合理管理。

### 5.4 并发
并发失控、缺并发限制、Goroutine 过多、锁竞争、死锁风险、高频定时任务、任务重复执行、Worker 无退出机制。

### 5.5 工具
`go pprof`（heap / goroutine / cpu / allocs / mutex / block）、runtime metrics。
**pprof 必须受保护**：只监听 loopback 或用 SSH 隧道，**禁止把未授权 pprof 接口暴露到公网**。

## 6. 第三阶段：Java / Spring Boot 深度内存优化

不要只看堆。必须同时考虑 JVM 堆与原生内存。

### 6.1 内存结构
Heap、Young / Old、Metaspace、Code Cache、Direct Buffer、Thread Stack、Native Memory。
检查 `-Xms / -Xmx / -XX:MaxMetaspaceSize / GC 参数 / Direct Memory / Thread Stack / 容器内存感知`。
**不要把最大堆调得很低**——必须结合容器限额与真实业务需求。

### 6.2 代码质量
对象长期引用、集合无限增长、静态变量持大对象、缓存无过期、无界队列、线程池过大、线程无法退出、数据库连接池过大、定时任务重复注册、重复加载配置、不必要对象创建、大量 JSON 序列化开销、不合理数据库查询。

### 6.3 GC 与线程
GC 次数/停顿、Old 区增长、Full GC 频率、线程数、线程栈大小、线程池队列长度、Direct Buffer 用量。
可用 `jcmd / jstat / jmap / JFR / NMT`。**若某项诊断需在 JVM 启动时加参数（如 NMT），必须先说明需要重启及其兼容性影响，不能直接改生产启动参数**——除非已获授权。

## 8. 第五阶段：Docker / Compose

### 8.1 资源
启动了多少容器、各跑什么、是否重复启动、是否有无效容器、多余后台进程、内存异常、资源限制缺失、重启策略不合理、不必要的资源重复使用。

### 8.2 内存管理
`memory limit / reservation`、CPU 限制、OOM 风险、cgroup 内存使用、容器内存缓存、RSS / PSS、日志占用、文件描述符、网络连接数。
**Docker 统计的内存与宿主机显示可能因缓存、共享内存而口径不同。不能把各容器数字简单相加当真实物理内存消耗**，必须结合 cgroup 与宿主机数据判断。

### 8.3 镜像
基础镜像过大、重复依赖、可否多阶段构建、构建工具是否进了生产镜像、不必要文件、无效构建缓存、镜像层重复。
**镜像体积优化 ≠ 运行内存优化**，不要把减小镜像当作降内存的唯一手段。

### 8.4 日志与存储
日志是否无限增长、是否缺轮转、临时文件积累、无效数据卷、不必要文件缓存、日志重复写入。改日志策略必须保留必要的故障追踪能力。

### 8.5 兼容性
保留 IPv4 / IPv6、网络与端口映射、数据卷、环境变量、服务依赖、启动命令、健康检查、节点通信能力。

## 9. 第六阶段：Shell 安装与部署脚本

**重点检查幂等性**：重复执行安装脚本不应导致重复安装服务、重复创建容器、重复启动进程、重复写配置、产生无法清理的后台任务。修改脚本必须保留原有安装与升级功能。

## 10. 第七阶段：服务器实际内存诊断

仅读源码无法判断生产真实情况。若能连测试服务器，在获授权后做**只读**诊断；否则给出可手动执行的命令集。

### 10.1 系统
`free -h`、`uptime`、`top -b -n 1`、`ps aux --sort=-%mem | head -30`、`cat /proc/meminfo`、`vmstat 1 5`、`df -h`

### 10.2 Docker
`docker stats --no-stream`、`docker ps -a`、`docker system df`、`docker compose ps`
每容器补充：名称、ID、PID、RSS、内存使用量、CPU、重启次数、运行时长。

### 10.3 进程
Go / Java / Node / Nginx / Docker 及常驻进程。优先用 **RSS**（实际驻留物理内存）、**PSS**（按共享比例分摊）、VSZ（虚拟内存）、线程数、FD 数。**不要只凭 VSZ 判断真实内存消耗。**

### 10.4 cgroup
`memory.current`、`memory.peak`（若支持）、`memory.max`、`memory.stat`、`memory.events`。按实际 cgroup 版本选正确路径。

### 10.5 内存分类（必须区分）
1. 应用实际使用的内存；2. 文件缓存；3. 内核缓存；4. 共享内存；5. JVM 原生内存；6. Go Runtime 管理的内存；7. 容器统计中的缓存部分。
**防止把 Linux 正常缓存行为误判成内存泄漏。**

## 11. 第八阶段：泄漏与长期运行检测

不能只看启动后几分钟。观测：启动 5 分钟 / 30 分钟 / 1 小时 / 6 小时 / 24 小时（按服务器条件调整）。

观察：空闲时内存是否持续增加；请求量增加后是否异常增加；请求结束后能否回落；GC 后变化是否合理；Goroutine 是否持续增长；Java 线程是否持续增长；TCP 连接是否持续积累；FD 是否持续增长；缓存是否持续增加；是否 OOM 或容器重启。

**进程释放对象后不一定立即把内存归还系统。不能仅凭 RSS 未立即下降就判定泄漏**，必须结合 Heap / PSS / cgroup / GC 与持续增长趋势。

## 12. 第九阶段：代码质量与架构优化

消除重复代码、减少不必要抽象、优化数据结构、数据库访问、缓存策略、连接池、并发控制、资源生命周期；清理确认无用的代码；减少不必要依赖、重复数据转换、无效网络请求；优化定时任务；改善错误处理；统一资源释放机制；减少不必要的后台常驻任务。

**不要单纯为代码行数少而牺牲可读性和可维护性。** 优先选择：**低风险、可验证、可回滚、收益明确**的方案。

## 13. 第十阶段：性能与安全边界

必须保证：不关闭安全校验；不降低认证安全性；不删除必要日志；不关闭 IPv6；不降低节点通信稳定性；不随意缩短超时导致请求失败；不随意限制并发导致业务能力下降；不设过低 JVM 最大堆；不盲目提高 Go GC 频率；**不通过 Docker 极低内存限制掩盖内存泄漏**。

**阶段五 交付结果**：完整修改记录、测试结果、部署说明。

## 19. 最终验收标准

**代码层面**：找出重复代码与不合理实现；找出有风险的内存管理方式；找出不合理的并发与资源管理；修复有证据支持的泄漏；减少不必要分配；改善长期运行稳定性。

**部署层面**：清楚服务器实际运行哪些服务；清楚每个服务用多少内存；清楚容器资源占用；排查重复进程与不合理配置；保留 IPv4 / IPv6；保留现有安装升级方式。

**功能层面**：所有现有功能不变；API 兼容；数据兼容；前端兼容；客户端兼容；多节点管理不受影响。

**真实性**：最重要。没有证据不要编造结论；没有实际测试不要声称优化成功；必须区分静态分析、实际运行数据与推测性风险；若某问题需真实服务器数据才能确定，明确列出需要收集什么数据。
